# KCC721 v0.2 blind mint

Status: implementation draft for controlled Mainnet tests.

KCC721 v0.2 numbers NFTs from `1` through `maxSupply`. Native collections use
a two-transaction blind mint so a buyer cannot inspect the NFT before payment.

## Shuffle commitment

Before genesis, the deployment tool creates a random permutation and a random
32-byte salt for each mint position:

```text
leaf = SHA256(LE64(mint_index) || LE64(token_id) || salt)
```

Genesis commits to the Merkle root. The private reveal artifact is retained by
the reveal service and included in backups. Publishing the complete artifact
after the final reveal proves that it is a permutation of `1..maxSupply` and
that no assignment changed after genesis.

## Commit and reveal

The buyer signs a commit that advances the singleton controller, enforces the
mint terms, and creates a ticket bound to the buyer's public key. The ticket
contains a mint position but no token ID.

After acceptance, the service supplies the committed token ID, salt, and path.
The ticket covenant verifies the proof and creates the NFT for the immutable
ticket recipient. The token and image appear in the interface only after the
reveal is accepted.

## Metadata validation

Genesis preparation accepts a valid immutable `ipfs://` collection root and
checks `1.json` plus `maxSupply.json`. Both must be JSON objects and contain an
immutable `ipfs://` image URI. The hosted service caps each metadata JSON
response at 16 MB to protect its own resources. This is not a KCC721 rule and
does not limit image size; image files are neither downloaded nor measured at
deployment.

## Canonical ticker

Ticker matching is case-insensitive. Conforming indexers assign a ticker to the
first valid accepted v0.2 genesis in canonical virtual-chain order and roll the
assignment back with reorgs. A covenant cannot inspect the entire BlockDAG, so
network-wide uniqueness is an indexer validity rule rather than a local script
condition.

## Trust boundary

The root prevents post-genesis reassignment but does not guarantee reveal-data
availability. Losing every copy can strand tickets. Deployers should keep an
encrypted export and replicate it across independent reveal providers before
opening a mint.
